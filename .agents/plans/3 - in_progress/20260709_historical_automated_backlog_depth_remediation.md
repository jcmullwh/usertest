# Make automated backlog planning evidence-driven and outcome-verifiable

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept current while work proceeds. It follows the binding instructions loaded from `.agents/PLANS.md` in the primary `I:\code\usertest` checkout.

## Purpose / Big Picture

The automated backlog currently turns observations into detailed-looking plans without reliably preserving where evidence came from, proving a root cause, consolidating same-cause problems, grounding plans in code, or checking whether completed work resolved the originating failure. After this change, each automated observation will retain its lineage, join a persistent canonical case, pass strict evidence gates before planning, and carry implementation and verification outcomes separately. A developer can demonstrate the result with offline tests that replay known historical failure patterns: research-derived observations update their parent case, partial research remains blocked, same-cause problems collapse before planning, shallow plans are rejected, and stale tickets are superseded rather than deleted.

## Context and Orientation

`packages/backlog_core` owns the stage schemas, relation review logic, ticket assembly, and policy. `packages/backlog_miner` executes model-backed stages and research runs. `apps/usertest_backlog` orchestrates the six-stage workflow and exports Markdown plans. Configuration and prompt guidance live under `configs/backlog_prompts`, `configs/backlog_stage_guidance`, and their internal-maintenance variants.

An atom is a single observed fact extracted from a run. A canonical case is the durable identity for the underlying problem across runs and wording changes. Derived evidence is an atom produced while researching or implementing an existing case; it updates that case by default instead of creating another independent problem. A material unknown is an unanswered question that could change the diagnosed cause, interface, or implementation surface.

The current pipeline mines problems, prioritizes them, runs research, generates three forced option families, selects one, and creates a plan. Relation review occurs too late and its annotations are discarded. Stage parsers retain malformed records as warnings. Research can be partial and still become ready. Downstream stages do not receive repository access. Export cleanup deletes stale generated files based on a prose-derived fingerprint. Queue state is then used as a proxy for outcome.

## Risks and mitigations

The main compatibility risk is invalidating legacy artifacts that lack new fields. Parsing will remain capable of reading them for audit, but new stage output and readiness decisions will be strict. Tests will distinguish legacy-read compatibility from new-write validity.

Another risk is false merging: two similar symptoms may have different causes. Canonical grouping will preserve symptom facets and explicit split decisions; it will not merge solely on wording similarity.

Fake success is the largest risk. Acceptance therefore requires historical regression scenarios and separate code-test, original-scenario, and live verification states. A plan cannot be ready merely because required-looking prose exists.

## Validation and Acceptance

Acceptance requires all high-severity atoms in a generated batch to have a disposition; derived research atoms must not create new cases without an explicit promotion; same-cause decisions must reduce downstream work units; materially partial research must remain research-required; ready plans must contain exact code targets and executable verification; and superseded files must remain traceable.

Historical regressions must show the fixed verification-path research updating its original case rather than creating three fresh tickets, while the Windows shell case remains mitigated or unresolved rather than resolved. Outcome records must identify target branch and distinguish tests from live proof.

## Idempotence and Recovery

Tests and historical replays are offline and may be rerun. The implementation must not rewrite the retained historical corpus. Any migration or backfill command added later must default to analysis-only and emit a new artifact rather than mutating source evidence. If a stage cannot meet a new contract, it must fail loudly or remain research-required.

## Artifacts and Notes

The original historical run artifacts remain outside this isolated worktree and are reference evidence only. Tests will use compact sanitized fixtures rather than mutating or depending on those operational directories.
